# 全局审计质量自我校验规范 (Self-Correction Guide)

大模型在执行长时间、多文件的代码审计时，容易产生认知偏差或逻辑跳跃。为了保证输出的漏洞报告具备极高的实战价值，在最终输出报告之前，**必须**执行以下自我校验（Self-Correction）步骤。

## 1. 逻辑闭环校验 (Logical Closure Check)
在你准备输出“确诊漏洞 (Exploitable)”结论之前，请在内心问自己以下三个问题：
- **Q1: 污染源是否真的可控？**
  *如果数据是从 `application.yml` 或 `System.getProperty` 读出来的，立刻推翻结论。*
- **Q2: 传播路径是否真的连通？**
  *我是不是只靠正则匹配了同名方法，而没有检查它们的 `import` 包名和实例类型？（详见 taint_analysis_rules.md）*
- **Q3: 是否遗漏了全局净化机制？**
  *我是否检查了项目中是否存在 `XssFilter`、`WafInterceptor` 或者针对全局参数的 HTML 实体转义？*

如果以上任何一个问题的答案是“否”或“不确定”，必须将风险降级为“潜在风险 (Needs Review)”，或者继续搜索直到找到确凿证据。

## 2. 漏洞利用前置条件校验 (Prerequisite Check)
某些漏洞的成立需要苛刻的环境或配置前提。在报告中必须声明这些前提是否满足：
- **组件漏洞**: 如 Jackson 反序列化，是否检查了应用确实启用了 `enableDefaultTyping` 或者传入了特定的多态类？
- **SQL 注入**: 如果是 `ORDER BY` 注入，是否确认了数据库驱动没有开启针对此字段的严格校验？
- **XXE**: 是否确认了当前使用的 JDK 版本？（高版本 JDK 默认可能已经限制了某些外部协议的获取）。

## 3. 修复建议的可落地性 (Actionable Remediation)
不要给出假大空的建议（如“建议过滤用户输入”）。
**必须**：
- 结合当前项目使用的框架（如 MyBatis, Spring Security）给出具体的代码级修复方案。
- 修复方案必须是向后兼容的（例如：把 `$` 改为 `#`，而不是建议重构整个 DAO 层）。

## 4. 报告精简原则 (Conciseness)
- **拒绝流水账**: 不要向用户复述你搜索文件的全过程（“我先找了A，然后找了B...”）。
- **直击要害**: 报告必须直接输出漏洞点、数据流向和修复建议。废话越少，审计报告的专业度越高。
